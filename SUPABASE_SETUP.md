## 2. Database Schema

The app uses a single shared key-value table, scoped per-user at the application layer.
Run this SQL once in the Supabase SQL editor:

```sql
-- Key-value store for Make (auto-generated by Figma Make)
CREATE TABLE IF NOT EXISTS kv_store_3fde14d4 (
  key  TEXT NOT NULL PRIMARY KEY,
  value JSONB NOT NULL
);

-- REQUIRED: keep RLS on with no policies. The table now also holds each user's
-- Google refresh token, and this is what stops anyone with the public anon key
-- from reading it (the edge function uses the service role key, which bypasses RLS).
ALTER TABLE kv_store_3fde14d4 ENABLE ROW LEVEL SECURITY;
```

Data is keyed as:
- `lists:<userId>`   — the user's custom list categories and items
- `watched:<userId>` — an array of YouTube video IDs the user has marked watched
- `google_rt:<userId>` — the user's Google refresh token (used to renew the ~1h Google access token; never sent to the browser)

## 3. Edge Function

The backend lives in `supabase/functions/server/`. Deploy it after any code change:

```bash
# Install the Supabase CLI if needed
npm install -g supabase

# Log in
supabase login

# Link to the project
supabase link --project-ref wcmdmlqwuuicyhoafmki

# Deploy the edge function
supabase functions deploy make-server-3fde14d4 --project-ref wcmdmlqwuuicyhoafmki
```

The function exposes these endpoints (all require a valid Supabase JWT as Bearer token):

| Method | Path                                    | Description                    |
|--------|-----------------------------------------|--------------------------------|
| GET    | /make-server-3fde14d4/health            | Health check (no auth needed)  |
| GET    | /make-server-3fde14d4/lists             | Load the current user's lists  |
| PUT    | /make-server-3fde14d4/lists             | Save the current user's lists  |
| GET    | /make-server-3fde14d4/watched           | Load watched video IDs         |
| POST   | /make-server-3fde14d4/watched           | Add a watched video ID         |
| PUT    | /make-server-3fde14d4/google/refresh-token | Store the user's Google refresh token (sent once, right after sign-in) |
| GET    | /make-server-3fde14d4/google/access-token  | Exchange the stored refresh token for a fresh Google access token |
| DELETE | /make-server-3fde14d4/google/refresh-token | Forget the stored token (sign-out) |

## 4. Google OAuth Setup

### 4a. Google Cloud Console

1. Go to https://console.cloud.google.com and create a project (or reuse one).
2. Enable these APIs:
   - **Google Calendar API**
   - **YouTube Data API v3**
3. Create **OAuth 2.0 Client ID** credentials (type: *Web application*).
4. Add the following **Authorized Redirect URI**:
   ```
   https://wcmdmlqwuuicyhoafmki.supabase.co/auth/v1/callback
   ```
5. Note the **Client ID** and **Client Secret**.
6. **OAuth consent screen → Publishing status: set it to _In production_.** While it says
   *Testing*, Google expires refresh tokens after **7 days**, so the app would ask you to
   reconnect weekly no matter what the code does. For a personal app you can stay
   unverified in production (you'll see an "unverified app" screen once; unverified apps
   are limited to 100 users).

### 4b. Supabase Auth Provider

1. Open https://supabase.com/dashboard/project/wcmdmlqwuuicyhoafmki/auth/providers
2. Find **Google** and enable it.
3. Paste in the Client ID and Client Secret from step 4a.
4. Save.

### 4c. OAuth Scopes used

The app requests these scopes at sign-in:

```
https://www.googleapis.com/auth/calendar
https://www.googleapis.com/auth/youtube
```

`calendar` lets the app create events. `youtube` is required to delete playlist items and
to run the search behind the random video of the day (`search.list`, 100 quota units per
call of the 10,000/day default; the pick is cached for the calendar day). If a user signed
in before the `youtube` scope was added they will see a "Reconnect Google" prompt once.

## 5. Environment Variables

### Frontend (Vite)

These are read from `utils/supabase/info.tsx` (auto-generated by Figma Make):

```ts
export const projectId = "wcmdmlqwuuicyhoafmki"
export const publicAnonKey = "<your-supabase-anon-key>"
```

To rebuild with a different project, update that file with the new values.

### Edge Function (Supabase secrets)

The edge function reads these from Deno's environment — Supabase injects them automatically:

| Variable                | Description                               |
|-------------------------|-------------------------------------------|
| `SUPABASE_URL`          | Your project's REST URL (auto-injected)   |
| `SUPABASE_ANON_KEY`     | Public anon key (auto-injected)           |
| `SUPABASE_SERVICE_ROLE_KEY` | Service role key (auto-injected)      |

These three need no configuration; Supabase provides them to every edge function.

**You must add two secrets yourself** (they are how the function renews Google access).
Use the *same* OAuth client whose ID/secret you pasted into Supabase in step 4b:

```bash
supabase secrets set GOOGLE_CLIENT_ID=<client id> GOOGLE_CLIENT_SECRET=<client secret> \
  --project-ref wcmdmlqwuuicyhoafmki
```

(or Dashboard → Edge Functions → Secrets). Then redeploy the function (section 3).
Without them `GET /google/access-token` answers `500 server_not_configured` and the app
shows a "Retry" banner instead of renewing the token.

## 6. Auth Settings (Supabase Dashboard)

To prevent the daily logout issue, confirm these settings in
https://supabase.com/dashboard/project/wcmdmlqwuuicyhoafmki/auth/url-configuration:

- **JWT Expiry:** 3600 (default) — the Supabase client auto-refreshes this.
- **Refresh Token Reuse Interval:** 10 seconds (default).
- **Max Session Length:** Ensure this is not set too short (default is indefinite or 1 week depending on plan).

> **How Google access survives overnight:** Google's `provider_token` (access token) lasts
> ~1 hour and Supabase never renews it — only the Supabase session refreshes. So the app
> now works like this:
>
> 1. At sign-in it requests `access_type=offline` and sends Google's `provider_refresh_token`
>    to the edge function, which stores it server-side (`google_rt:<userId>`).
> 2. Whenever its cached access token is missing or expired (or Google answers 401), it calls
>    `GET /google/access-token`; the function exchanges the refresh token with Google
>    (using the client secret, which never reaches the browser) and returns a fresh token.
> 3. The "Reconnect Google" banner now only appears if Google rejects the refresh token
>    itself (access revoked, or the consent screen is still in *Testing* — see 4a step 6).
>    That one-time reconnect stores a new refresh token.
>
> Anyone who signed in before this change has no stored refresh token yet: they see
> "Reconnect Google" once, and that sign-in stores it.

## 7. PWA / Push Notifications

The app uses the Web Notifications API (`new Notification(…)`). This requires:

1. The user grants notification permission when prompted.
2. The app must be open (or at least recently active) in the browser to fire the notification.
3. A "video of the day" notification fires once per calendar day, tracked via localStorage key `reel.last_notif_date`.

For true background push notifications (when the app is closed), you would need:
- A Push API subscription + Service Worker
- A backend job (e.g., a Supabase scheduled edge function) to send push messages daily
